# 블로그 렌더링을 ISR로 정한 이유와 재검증의 실제 동작

블로그 페이지를 SSR도 CSR도 아닌 ISR로 렌더링하기로 한 판단과, "재검증"이 런타임에
정확히 무엇을 하는지 정리한다.

`docs/blog-search-route-separation.md`는 **경로를 어떻게 나눌지**(검색과 페이지네이션을
별도 라우트로 뺀 이유)를 다루고, 그 5절에서 순수 SSG를 기각한 이유를 짧게 언급한다.
이 문서는 그 앞 단계인 **렌더링 방식 자체의 선택**과, 선택한 방식이 실제로 어떻게
도는지를 다룬다.

## 1. 배경

블로그를 만드는 목적은 검색 유입과 `to-teacher.com`의 주제 전문성·신뢰도 강화다
(`docs/blog.md` 1장). 즉 **크롤러가 콘텐츠를 온전히 읽어갈 수 있는지**가 다른 모든
고려사항보다 앞선다. 동시에 글은 운영 중에 계속 추가되고, 예약 발행(5.4)도 쓴다.
프론트 배포와 무관하게 새 글이 노출돼야 한다는 뜻이다.

이 두 요구가 렌더링 방식 선택을 사실상 결정한다.

## 2. 후보 비교

| 방식                  | 크롤러가 받는 것 | 새 글 반영      | 응답 속도                    | 백엔드 부하    |
| --------------------- | ---------------- | --------------- | ---------------------------- | -------------- |
| SSG (완전 정적)       | 완성된 HTML      | 재배포해야 반영 | 가장 빠름                    | 빌드 때 1회    |
| SSR (매 요청 렌더)    | 완성된 HTML      | 즉시            | 백엔드 응답 시간에 묶임      | 요청 수에 비례 |
| CSR (클라이언트 렌더) | 빈 껍데기        | 즉시            | 셸은 빠르나 콘텐츠는 JS 이후 | 요청 수에 비례 |
| **ISR (채택)**        | 완성된 HTML      | 재검증 주기 내  | 프리렌더된 HTML 그대로       | 주기당 1회     |

### 2.1 CSR 기각 — 목적 자체가 무너진다

크롤러가 받는 HTML이 빈 셸이면 색인할 본문이 없다. 구글은 JS를 실행하긴 하지만
렌더링을 별도 큐에 미뤄 처리하므로 색인이 지연되고, 네이버 크롤러와 카카오톡·슬랙 등
SNS 미리보기 봇은 대체로 JS를 실행하지 않는다. 검색 유입과 공유 카드가 존재 이유인
페이지에서 이 방식은 선택지가 아니다.

### 2.2 SSR 기각 — 느려서다, 신선하지 않아서가 아니다

SSR은 콘텐츠 신선도 면에서는 문제가 없다. 기각 이유는 비용 쪽이다.

- **TTFB가 백엔드 응답 시간에 그대로 묶인다.** 프리렌더된 HTML이 없으므로 모든 요청이
  백엔드 왕복을 기다린다. LCP는 구글 랭킹 시그널이고, 가장 많이 색인될 목록 페이지의
  속도를 깎는 선택이 된다.
- **백엔드 부하가 트래픽에 비례한다.** 5분 동안 1000명이 `/blog`에 들어오면 백엔드
  호출도 1000번이다. 검색 유입이 늘어나는 것이 이 프로젝트의 성공 지표인데, 성공할수록
  백엔드가 아파지는 구조가 된다. 같은 상황에서 ISR은 호출이 1번이다.
- **블로그 글은 초 단위 신선도가 필요 없다.** SSR이 주는 이점의 값이 이 도메인에서는
  낮다. 반대로 신선도가 실제로 필요한 댓글은 ISR에 얹지 않고 클라이언트에서 따로
  조회한다(`docs/superpowers/specs/2026-07-29-blog-design.md` 6장).

### 2.3 SSG 기각

예약 발행이 동작하지 않고, 발행 15분 뒤 나가는 뉴스레터의 링크가 404가 되며, 빌드가
백엔드 가용성에 묶인다. 자세한 내용은 `docs/blog-search-route-separation.md` 5절.

## 3. "재검증"이 실제로 하는 일

이름 때문에 오해하기 쉽지만, **"바뀌었는지 확인한다"가 아니라 "조건 없이 다시
렌더링한다"**는 뜻이다. Next.js가 백엔드에 변경 여부를 묻거나 ETag를 비교하지 않는다.
페이지 렌더를 처음부터 다시 실행해 결과로 캐시를 교체할 뿐이다.

### 3.1 타이머가 아니라 요청이 방아쇠다

크론이나 백그라운드 스케줄러는 존재하지 않는다. Next.js는 캐시 엔트리에 생성 시각만
같이 저장해 두고, **요청이 들어왔을 때** `지금 - 생성시각 >= revalidate`를 계산한다.
요청이 없으면 아무 일도 일어나지 않는다.

요청 시점의 캐시 상태에 따라 세 갈래로 갈린다.

| 캐시 상태        | 이 요청자가 받는 것         | 백엔드 호출        |
| ---------------- | --------------------------- | ------------------ |
| 없음             | 렌더링을 **기다린 뒤** HTML | 지금, 동기적으로   |
| 있음 + 주기 이내 | 캐시된 HTML 즉시            | 없음               |
| 있음 + 주기 경과 | **낡은 HTML 즉시**          | 응답 후 백그라운드 |

세 번째가 stale-while-revalidate다. 캐시가 낡았다고 요청자를 기다리게 하지 않는다.
낡은 것을 그대로 응답하고, 그 뒤 백그라운드에서 렌더링을 다시 돌려 캐시를 교체한다.
**그 요청자는 재생성의 방아쇠 역할만 하고 새 내용은 보지 못한다.** 새 내용은 그 다음
방문자부터 보인다.

```
빌드        렌더링 → 캐시 저장 (나이 0초)
0~300초     방문자 전원 캐시된 HTML 즉시 수신, 백엔드 호출 0회
301초 방문  ① 낡은 HTML을 그대로 응답
            ② 응답 후 백그라운드 재렌더링 → 새 HTML로 캐시 교체
그다음 방문  새 HTML 수신 (나이 0초로 리셋)
```

따라서 체감 지연은 "최대 5분"이 아니라 **"최소 5분 + 다음 방문까지"**다. 새벽에 글을
발행하고 아무도 들어오지 않으면 아침 첫 방문자는 여전히 어제 목록을 본다. 트래픽이
낮을수록 지연이 길어지는 성질이 있다.

재생성 단위는 경로별이다. `/blog`, `/blog/page/2`, `/blog/{slug}`가 각자 캐시 엔트리와
각자의 나이를 가진다.

### 3.2 캐시 층이 둘이라 300을 두 곳에 적는다

App Router에는 성격이 다른 캐시가 두 개 있고, 우리는 둘 다 300초로 맞춘다.

| 대상             | 설정 위치                          | 캐시하는 것       |
| ---------------- | ---------------------------------- | ----------------- |
| Full Route Cache | 라우트의 `export const revalidate` | 렌더링 결과 HTML  |
| Data Cache       | `fetch`의 `next: { revalidate }`   | fetch 응답 데이터 |

두 값이 어긋나면 결과가 어긋난다. 데이터 캐시가 10분인데 라우트가 5분이면, 5분 뒤
재렌더링을 돌려도 캐시된 옛 데이터를 다시 읽어 같은 HTML이 나온다. 그래서
`getBlogPosts`가 호출부에서 받은 `revalidate`를 fetch 옵션으로 그대로 넘긴다.

세그먼트 설정은 빌드 타임에 정적으로 분석되므로 `export const revalidate`에는 상수를
쓸 수 없고 리터럴이어야 한다. 그래서 각 라우트에 `300`이 중복되고,
`BLOG_REVALIDATE_SECONDS`는 fetch 옵션에만 쓴다. **값을 바꿀 때 양쪽을 함께 고쳐야
한다.**

한 가지 더. Next.js 15부터 `fetch`의 기본값은 `no-store`이므로, 재검증 주기를 명시하지
않으면 데이터가 캐시되지 않고 해당 라우트가 동적 렌더링으로 전환된다. ISR을 의도했다면
fetch 쪽 옵션을 빠뜨리면 안 된다.

## 4. `generateStaticParams`는 화이트리스트가 아니라 워밍업 목록이다

`/blog/[slug]`의 `generateStaticParams`는 빌드 타임에 최신 50개 글의 slug를 반환하고,
Next.js는 그 경로들의 HTML을 미리 구워 둔다.

문제는 빌드 이후 발행된 51번째 글이다. 그 slug는 목록에 없다. 기본값
(`dynamicParams = false`)이면 목록에 없는 경로는 **무조건 404**가 되므로, 새 글이 곧바로
404가 되는 사고가 난다. 그래서 `dynamicParams = true`로 켜 둔다. 이러면 목록에 없는
경로도 404 대신 **첫 요청에서 렌더링된 뒤 캐시**되고, 두 번째 방문자부터는 미리 구워둔
글과 동일하게 동작한다.

정리하면 `generateStaticParams`는 "이 경로만 허용"이 아니라 "이 경로들은 미리 만들어
둬"라는 의미다. 페이지네이션 경로(`/blog/page/[page]`)도 같은 이유로 `dynamicParams`를
켜 둔다.

부수적으로, 두 라우트의 `generateStaticParams`는 API 호출 실패 시 빈 배열을 반환한다.
빌드가 백엔드 가용성에 묶이지 않게 하려는 것이고, 미생성 경로는 위 규칙에 따라 요청
시 렌더링된다.

## 5. 이 선택으로 얻는 것과 감수하는 것

얻는 것

- 크롤러와 사용자 모두 프리렌더된 HTML을 받는다. SEO와 LCP 측면에서 SSG와 동일하다.
- 새 글·예약 발행이 재배포 없이 반영된다.
- 백엔드 부하가 트래픽과 분리된다. 주기당 경로별 1회다.
- `sitemap.xml`과 `rss.xml`에도 같은 주기를 걸어, 빌드 시점 목록이 박제되지 않는다.

감수하는 것

- 콘텐츠가 최대 재검증 주기(+다음 방문까지)만큼 낡을 수 있다.
- 낡은 캐시를 처음 만난 방문자는 새 내용을 보지 못한다.

## 6. 한계와 남은 과제

- **배포하면 캐시가 초기화된다.** 새 빌드 ID가 생기면서 Full Route Cache도 처음부터
  다시 쌓인다. 같은 이유로 이미지 최적화 캐시도 배포마다 사라지는데, 그 문제는
  `docs/blog-image-optimization-cache.md`에서 따로 다룬다.
- **인스턴스를 늘리면 캐시가 공유되지 않는다.** 셀프 호스팅에서 ISR 캐시는 각 인스턴스의
  파일 시스템에 있다. 다중 인스턴스로 확장할 때는 공유 캐시 핸들러가 필요하다.
  (`src/app/api/consent/route.ts`의 인메모리 레이트 리미트와 같은 성격의 제약이다.)
- **on-demand 재검증을 붙이면 지연을 없앨 수 있다.** 발행 흐름이 글을 `PUBLISHED`로
  전환한 뒤 프론트의 재검증 엔드포인트를 호출해 `revalidatePath`를 실행시키는 방식이다.
  그렇게 되면 300초는 그것이 실패했을 때의 안전망 역할만 하므로 값을 늘려도 된다.
  백엔드 발행 흐름이 확정된 뒤 추가한다.
