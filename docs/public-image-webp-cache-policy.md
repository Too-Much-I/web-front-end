# public/ 이미지: 미리 WebP 변환 + 30일 브라우저 캐시 + PR 검사

`public/` 이미지를 어떻게 최적화하고 캐시할지 정한 기록이다. `next/image` 런타임 변환, 서버 캐시 볼륨, CDN을 검토했다가 내려놓고 "미리 변환해서 커밋 + 브라우저 캐시 30일 + PR에서 강제"로 정한 이유를 정리한다. 반영 PR은 #120이고, 앞선 랜딩 경량화(#117)의 후속이다. 랜딩 작업 자체는 `docs/landing-asset-optimization.md`에 있다.

## 1. 출발점

#117에서 랜딩 히어로를 손으로 WebP로 바꿔 2MB를 130KB로 줄였다. 그 뒤 나온 질문은 "앞으로 이미지를 바꿀 때도 매번 사람이 변환해야 하나"였다.

- AI로 만드는 이미지는 거의 다 PNG라서, 변환을 잊고 그대로 올릴 가능성이 높다.
- 사람이 매번 챙겨야 하는 방식은 언젠가 2MB짜리가 다시 들어온다.

그래서 처음에는 자동으로 변환해 주는 `next/image`로 옮기는 쪽이 유력했다.

## 2. 처음 유력했던 안: next/image 런타임 변환

`next/image`는 별도 서버가 아니라 지금 Docker로 돌리는 Next 서버 안의 `/_next/image` 핸들러가 변환한다. 원본 PNG를 `public/`에 넣고 `<Image>`로 쓰기만 하면 리사이즈, WebP 변환, `srcset`, lazy loading을 알아서 해 준다. 레포에서도 이미 40곳 정도 쓰고 있었다.

감수할 점도 있었다.

- **배포마다 재변환:** 변환 결과는 컨테이너 안 `.next/cache/images`에 쌓여서, 컨테이너를 새로 띄우는 배포마다 사라진다. 배포 직후 첫 방문자는 변환을 기다린다.
- **서버 자원 사용:** 변환(sharp)은 CPU와 메모리를 꽤 쓴다. 캐시가 빈 순간에는 같은 서버의 페이지 응답과 자원을 나눠 쓴다.
- **CSS 배경에는 못 쓴다:** 수채화 타일 같은 `background-image`는 어차피 미리 변환해야 한다.

## 3. 캐시를 어디에 둘 것인가

"한 번 변환한 걸 계속 쓰고 싶다"는 목적에는 CDN이 꼭 필요하지 않다. 캐시를 둘 수 있는 위치는 세 군데이고, 각각 효과를 보는 대상이 다르다.

| 방식                            | 캐시 위치       | 줄어드는 것      | 효과를 보는 사람 |
| ------------------------------- | --------------- | ---------------- | ---------------- |
| 미리 변환해서 커밋              | 레포(빌드 전)   | 변환 비용 전부   | 모든 방문자      |
| next/image 캐시를 볼륨으로 유지 | 서버 디스크     | 재배포 후 재변환 | 첫 방문자        |
| 브라우저 캐시 헤더              | 사용자 브라우저 | 요청 자체        | 재방문자         |

- 서버 캐시는 변환 시간을 없애 줄 뿐, 이미지 전송은 매번 일어난다.
- 브라우저 캐시는 `max-age` 안에서는 요청을 아예 보내지 않는다. 기간이 지나도 안 바뀌었으면 304(본문 없음)로 가볍게 끝난다. 다만 브라우저가 저장 공간이 부족하면 지울 수 있다.
- Lighthouse는 매번 캐시 없이 재므로, LCP 점수에는 앞의 두 방식만 반영되고 브라우저 캐시는 안 잡힌다.
- CDN이 풀어 주는 건 거리 지연과 트래픽 분산이다. 사용자가 거의 국내이고 트래픽이 작은 지금은 우선순위가 낮다. CDN 구성안 비교는 `docs/blog-image-optimization-cache.md` 4절에 있다.

이 시점의 잠정 결론은 "next/image + 정적 import + 캐시 볼륨 + 브라우저 캐시"였다. 남은 확인은 서버가 이걸 감당하느냐였다.

## 4. 결정을 바꾼 것: 서버 실측

웹 서버(EC2, 서울 리전)에 접속해 직접 확인했다. 도메인이 CDN이나 로드밸런서 없이 이 EC2를 바로 가리키고, 앞에서 nginx가 받아 Next 컨테이너로 넘기는 구조다.

### 4.1 디스크는 문제가 없다

```
/dev/root  28G  15G used  14G avail  52%
```

변환된 WebP는 한 장에 10~~150KB라서, 이미지 50장에 너비 3~~4종을 곱해도 수십 MB다. 남은 14GB에 비하면 무시할 수준이다. 디스크를 차지하는 건 오히려 쓰지 않는 예전 Docker 이미지였다. 35개 중 4개만 사용 중이고 약 4GB가 회수 가능했다. 배포 스크립트의 `docker image prune -f`가 태그 없는 이미지만 지우기 때문이다.

### 4.2 메모리가 진짜 병목이다

```
Mem:   951Mi total   722Mi used   229Mi available
Swap:  2.0Gi total   385Mi used
```

| 프로세스                           | 메모리(RSS)  |
| ---------------------------------- | ------------ |
| next-server (웹 프론트)            | 165MB        |
| java -jar /app.jar (Spring 백엔드) | 155MB + 스왑 |
| dockerd, containerd, shim          | 약 73MB      |
| ssm-agent, snapd, sshd 등          | 약 40MB      |

- 1GB 인스턴스 한 대에 Next와 Spring이 같이 돈다. 누수가 있는 게 아니라 원래 이 정도다.
- 여유 메모리는 약 230MB이고, 이미 스왑을 385MB 쓰고 있다. 스왑은 RAM보다 훨씬 느려서 쓰는 순간 응답이 느려진다.
- sharp는 큰 이미지 한 장에도 수십~수백 MB를 쓴다. 변환이 몇 개 겹치면 스왑이 더 늘어 페이지까지 느려지거나, 최악에는 메모리 부족으로 컨테이너가 죽을 수 있다.
- 쓰지 않는 AI 채점 컨테이너는 메모리를 거의 쓰지 않아서, 내려도 메모리는 늘지 않는다. 웹은 더 이상 채점을 하지 않고, 앱의 API는 별도 로드밸런서를 쓰므로 이 서버와 관계가 없다.

**결론: 이 서버에서는 런타임 이미지 변환을 늘리면 안 된다.** 디스크 여유와 상관없이, 변환하는 순간의 메모리가 부족하다. 그래서 2절의 next/image 이전과 3절의 캐시 볼륨은 지금 사양에서는 택하지 않았다.

## 5. 최종 결정

### 5.1 이미지는 미리 WebP로 변환해서 커밋한다

서버는 파일을 내려주기만 하므로 메모리와 CPU를 거의 쓰지 않는다. 변환 비용은 개발자 로컬에서 한 번만 든다.

### 5.2 public/ 이미지에 30일 브라우저 캐시를 건다

설정하지 않은 기존 값은 Next 기본값 `Cache-Control: public, max-age=0`이었다. 브라우저가 저장은 하지만 쓸 때마다 "바뀌었어?"를 물어서, 이미지가 많은 메인은 재방문 때도 왕복이 수십 번 생겼다.

`next.config.ts`의 `headers()`로 `public, max-age=2592000`(30일)을 붙였다. 서버 부담이 0이고, 오히려 서버로 오는 요청이 줄어든다.

- `/_next/static/`은 Next가 이미 1년 immutable로 내려주므로 덮어쓰지 않게 제외했다.
- 페이지 HTML에는 적용되지 않는다.

### 5.3 변환을 잊지 않도록 PR에서 강제한다

사람의 기억에 맡기지 않기 위해 두 가지를 만들었다.

- **PR 검사(`.github/workflows/image-check.yml`):** `public/`이 바뀐 PR에서만 돌고, 의존성 설치 없이 git과 파일 시스템만 쓴다. 규칙은 `scripts/image-policy.mjs` 한 곳에서 관리한다.
- **변환 명령(`pnpm images:webp`):** main에 없는 새 PNG·JPG를 WebP로 바꾸고 원본을 지운다. `src/`에서 그 경로를 참조하던 곳도 `.webp`로 고친다.

CI가 직접 변환해서 커밋까지 해 주는 방식도 가능했지만, 검사는 CI가 하고 변환은 로컬 명령으로 하는 쪽을 택했다. 코드의 `.png` 경로까지 같이 고쳐야 해서, 사람이 결과를 보고 커밋하는 편이 안전하다.

### 5.4 같은 이름으로 내용만 바꾸는 것도 막는다

30일 캐시를 걸면 새 문제가 생긴다. 같은 파일 이름으로 내용만 바꾸면, 이미 받아 둔 사용자는 최대 30일 동안 옛 이미지를 본다. 브라우저가 그동안 서버에 묻지 않기 때문이다.

그래서 이미지 내용을 바꿀 땐 파일 이름도 바꾸는 규칙을 정하고, 이것도 CI로 막았다. 같은 이름 재사용은 세 경우가 있어서 모두 잡는다.

- 기존 파일을 덮어쓴 경우(git 상태 M)
- main에서 예전에 지운 경로를 다시 추가한 경우(A)
- 다른 파일을 예전에 쓰던 이름으로 바꾼 경우(R)

## 6. PR 검사 규칙 요약

| 규칙                              | 이유                                                            |
| --------------------------------- | --------------------------------------------------------------- |
| 새 PNG·JPG 금지                   | WebP보다 수 배 크다. AI 생성 이미지가 대부분 PNG다.             |
| 한 장 500KB 초과 금지             | 메인 히어로 WebP가 130KB 정도다.                                |
| PNG를 base64로 감싼 SVG 금지      | #117의 히어로처럼 벡터가 아니라 PNG 껍데기라 오히려 33% 커진다. |
| 이미 쓰던 이름의 이미지 변경 금지 | 30일 캐시 동안 옛 이미지가 보인다.                              |

**예외:** 링크 미리보기(`og-image*`), JSON-LD 로고(`logo*.png`), 파비콘과 아이콘은 PNG로 남겨도 된다. 외부 서비스가 읽는 이미지라 WebP 지원을 장담할 수 없다. 이들도 내용을 바꿀 땐 `og-image-v2.png`처럼 이름을 바꿔야 해서 접두사로 허용한다.

## 7. 함께 정리한 것: 마스코트 PNG

검사는 새로 들어오는 파일만 막기 때문에, 기존 파일은 따로 정리했다. `public/mascots/`의 PNG 36장이 38MB였고, `smile.png` 한 장이 3.3MB였다. 이 마스코트들은 27곳에서 `next/image`로 쓰여서, 4절의 1GB 서버가 런타임에 3MB짜리 PNG를 변환하고 있었다.

- 36장을 WebP로 바꿔 38MB를 3MB로 줄였다.
- 원본 PNG를 지웠기 때문에, 그 URL을 외부에서 직접 쓰던 곳은 깨진다. 모바일 앱 레포는 웹 이미지 URL을 쓰지 않는 것을 확인했다.
- 투명 배경도 원본과 같게 나오는 것을 확인했다.

## 8. 이미지를 추가하거나 바꿀 때

1. PNG나 JPG를 `public/`에 넣는다.
2. `pnpm images:webp`를 실행한다. WebP 변환과 코드 경로 수정이 한 번에 된다.
3. 기존 이미지를 교체하는 거라면 새 이름(예: `-v2`)으로 넣고 참조 경로를 바꾼다.
4. 로컬에서 미리 확인하려면 `pnpm images:check`를 실행한다.

## 9. 다시 검토할 시점

지금 결정은 "1GB 서버에 Next와 Spring이 같이 돈다"는 전제 위에 있다. 아래 중 하나라도 바뀌면 2절의 next/image 이전과 캐시 볼륨을 다시 본다.

- 인스턴스를 키울 때(예: 2GB급). 스왑 문제가 대부분 사라진다.
- 프론트와 백엔드를 다른 서버로 나눌 때.
- JVM 힙 상한(`-Xmx` 또는 `-XX:MaxRAMPercentage`)을 걸어 메모리 여유가 생길 때. 백엔드 담당과 상의할 일이다.

CDN은 해외 트래픽이 생기거나 인스턴스를 2대 이상으로 늘릴 때 본다. 기준은 `docs/blog-image-optimization-cache.md` 7절과 같다.

## 10. 남은 과제

- **블로그 썸네일의 런타임 변환:** `docs/blog-image-optimization-cache.md`는 next/image 캐시를 볼륨으로 유지하는 안을 채택했다. 하지만 4절의 메모리 상황을 보면, 썸네일이 쌓였을 때 배포 직후 변환이 몰리는 게 부담이 될 수 있다. 그 문서 4.4절처럼 업로드할 때 WebP로 만들어 올리는 쪽을 우선 검토할 만하다.
- **오래된 Docker 이미지 정리:** 회수 가능한 약 4GB가 쌓여 있다. 배포 스크립트의 prune 범위를 넓힐지 정해야 한다.
- **참조 없는 마스코트:** `exiting_rabbit`, `no_score`, `rabbit_tight`는 `src/`에서 쓰지 않는다. 필요 없으면 지운다.
- **영상:** `mp4`, `webm`은 이번 캐시와 검사 대상에서 뺐다.
