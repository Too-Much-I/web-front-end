# 앱 설정 화면 웹뷰 페이지 설계

작성일: 2026-08-03

> 이 문서가 다루는 것은 **이 레포에서 만들 웹뷰 페이지 3장**이다. 설정 화면 자체는
> React Native 앱 레포에서 네이티브로 구현하며, 여기서는 그 화면이 무엇을 웹뷰로
> 띄우는지와 그 계약만 정의한다.

## 1. 배경과 결정

앱의 설정 화면을 만들면서 "웹뷰 vs 네이티브"를 정해야 했다. 웹뷰의 장점은 스토어
심사 없이 갱신된다는 것이고, 네이티브의 장점은 다른 탭과 동일한 셸·스크롤·폰트다.

설정 화면의 항목을 갈라 보면 **자주 바뀌는 것과 거의 안 바뀌는 것이 이미 깔끔하게
나뉘어 있다.** 설정 리스트 자체는 1년에 몇 번 안 바뀌지만, 개인정보 처리방침과
이용약관은 법령 대응으로 예고 없이 바뀐다. 심사 없이 갱신되어야 하는 건 후자뿐이다.

또한 목업 항목 중 절반이 네이티브 능력에 묶여 있다 — 학습 알림 토글(푸시 권한과
토큰), 앱 평가하기(스토어 리뷰 API), 버전 정보, 학습 기록 삭제(기기 저장소). 설정
화면 전체를 웹뷰로 만들면 항목마다 `postMessage` 브릿지를 만들어야 하는데, **그
브릿지야말로 스토어 심사를 거쳐야 바뀐다.** 웹뷰로 얻으려던 갱신 속도가 거기서
사라진다.

**결정: 셸은 네이티브, 문서성 페이지만 웹뷰.**

| 항목                     | 어디       | 근거                                    |
| ------------------------ | ---------- | --------------------------------------- |
| 하단 탭바, 리스트, 배너  | RN         | 다른 탭과 같은 셸. 거의 안 바뀜         |
| 학습 알림 토글           | RN         | 푸시 권한·토큰 등록                     |
| 앱 평가하기              | RN         | `expo-store-review`                     |
| 버전 정보                | RN         | `expo-application`                      |
| 모든 학습 기록 삭제      | RN         | 기기 저장소 + 서버 삭제 API             |
| **개인정보 처리방침**    | **웹뷰**   | 법령 대응으로 예고 없이 바뀜            |
| **이용약관**             | **웹뷰**   | 위와 동일                               |
| **문의하기**             | **웹뷰**   | 문구·연락 수단이 자주 바뀜              |
| 마이크 테스트            | 1차 제외   | 시험 녹음 구조 확정 후 결정             |
| 음향 테스트              | 1차 제외   | 위와 동일                               |

기각한 대안:

- **설정 전체 웹뷰** — 위에 적은 브릿지 문제. 더해서 탭바만 네이티브이고 본문이
  웹뷰면 스크롤 바운스와 폰트가 다른 탭과 미묘하게 어긋난다.
- **전부 네이티브(약관 본문 포함)** — 약관 한 글자 고치는 데 스토어 심사가 필요하고,
  업데이트하지 않은 사용자는 옛 약관을 계속 본다. 동의 버전을 별도로 관리하는
  프로젝트(`VOICE_CONSENT_VERSION`, `src/features/consent/consent-content.ts`)에서는
  특히 나쁘다.

## 2. 구현 범위

**포함** — `/app-settings` 아래 웹뷰 페이지 3장(개인정보 처리방침, 이용약관,
문의하기), 이들이 공유하는 앱 전용 문서 레이아웃 1개, 그리고 `app-*` 웹뷰
라우트에서 웹 분석 도구를 걷어내는 게이트 1개(6절).

**제외** — RN 설정 화면, 마이크·음향 테스트, 웹의 기존 `/privacy`·`/terms`·`/contact`
변경. 기존 웹 페이지는 손대지 않는다.

## 3. 라우트 구조

기존 앱 웹뷰 관례(`app-exam-screen`, `app-question-feedback`)의 `app-` 접두사를
따르되, 셋이 같은 셸을 쓰므로 한 단계 묶는다.

```
src/app/app-settings/
  layout.tsx        # robots noindex + 앱 웹뷰 공통 셸
  privacy/page.tsx  # 앱 전용 본문 (신규 작성)
  terms/page.tsx    # 앱 전용 본문 (신규 작성)
  contact/page.tsx  # 웹 본문 재사용, 크롬만 제거
```

`layout.tsx`는 `app-exam-screen/layout.tsx`와 같이 `robots: { index: false, follow:
false }`를 둔다. 앱 안에서만 열리는 화면이 검색에 잡히면 웹 사이트의
`/privacy`·`/terms`와 중복 색인된다.

## 4. 컴포넌트와 디자인

새로 만드는 것은 `src/components/app-settings/app-doc-layout.tsx` 하나다. 웹의
`LegalPageLayout`(`src/components/legal/legal-page-layout.tsx`)에서 **헤더와 푸터만
걷어낸 형태**다.

걷어내는 이유가 있다. 웹 레이아웃의 헤더에는 로고와 "홈으로" 링크가, 푸터에는
"홈으로 돌아가기"가 있다. 웹뷰에서 이걸 그대로 띄우면 사용자가 앱 안에서 마케팅
랜딩 페이지로 빠져나가 갇힌다.

유지하는 것:

- 시각 언어 — `bg-orange-50/40` 바탕, `text-blue-950` 제목, `text-zinc-600` 본문.
  새 색을 만들지 않는다.
- 제목 + 시행일 + 도입문 구조.
- **`LegalSection`은 그대로 재사용한다.** 이미 크롬이 없고 조문 하나를 그리는
  역할만 한다. 재사용하면 웹과 앱의 조문 모양이 자동으로 같아지고, 조문 타이포를
  고칠 때 한 곳만 고치면 된다.

반응형은 CLAUDE.md의 규칙을 따라 `sm → md → lg → xl`을 함께 정의한다. 다만 이
페이지들은 앱 웹뷰 전용이라 실사용 폭이 모바일에 몰려 있으므로, 최대 폭은 웹
법률 페이지의 `max-w-3xl` 대신 `max-w-2xl`로 잡아 본문 줄 길이를 유지한다.

## 5. RN과의 계약

앱 레포에서 구현할 몫이지만, 이 설계가 전제하는 것이므로 여기 남긴다.

1. **화면 헤더는 RN이 그린다.** 웹 페이지에는 뒤로가기 버튼도 타이틀바도 없다.
   따라서 상단 safe-area는 웹이 다루지 않고, 하단만 `env(safe-area-inset-bottom)`으로
   처리한다.
2. **외부 링크는 웹뷰 밖으로 넘긴다.** 문의하기의 `mailto:`와 Gmail 작성 링크가
   웹뷰 안에서 열리면 앱이 메일 화면에 갇힌다. RN의 `onShouldStartLoadWithRequest`에서
   `http(s)`가 아닌 스킴과 `mail.google.com`을 `Linking.openURL`로 넘겨야 한다.
3. **URL은 경로 고정.** `/app-settings/privacy`, `/app-settings/terms`,
   `/app-settings/contact` 세 개가 계약이며 쿼리 파라미터는 쓰지 않는다.

## 6. 웹 분석 도구 제외

루트 레이아웃(`src/app/layout.tsx`)이 Microsoft Clarity와 Google Analytics를 모든
페이지에 마운트하고 있어, 기존 `app-exam-screen`·`app-question-feedback`을 포함한
앱 웹뷰 화면에도 두 도구가 붙어 있었다. 이를 걷어낸다.

**근거:** 웹뷰에 웹 분석 SDK를 그대로 두면 같은 사용자가 네이티브 세션과 웹
세션으로 쪼개진다. 이용자 수가 중복 집계되고, 네이티브 화면에서 웹뷰 화면으로
넘어가는 퍼널이 끊긴다. 네이티브와 웹뷰를 섞을 때의 정석은 분석 SDK를 네이티브에
하나만 두고, 웹뷰 화면의 이벤트는 `window.ReactNativeWebView.postMessage`로 넘겨
네이티브 SDK로 기록하는 것이다.

**방법:** 경로 접두사로 가르는 클라이언트 컴포넌트
`src/components/analytics-gate.tsx`를 두고 루트 레이아웃이 이것만 렌더한다.
`/app-`으로 시작하는 경로에서는 아무것도 렌더하지 않는다. 앱 웹뷰 라우트는 이미
`app-` 접두사를 관례로 쓰고 있고, 웹 라우트 중에는 이 접두사로 시작하는 것이 없다.

라우트 그룹(`(web)`/`(app)`)으로 가르는 방법도 있고 분석 스크립트가 앱 라우트
번들에 아예 들어가지 않는다는 장점이 있지만, 기존 라우트 디렉터리를 전부 옮겨야
해서 이 작업에 비해 변경 범위가 크다. 접두사 게이트로 충분하다.

**앱 쪽 분석 도구는 이 문서의 범위 밖이다.** 앱 레포에서 정한다. 다만 도구를
도입하면 앱용 개인정보 처리방침의 위탁·국외 이전·자동 수집 장치 조문을 함께
갱신해야 한다(7.2 참고).

## 7. 본문 내용

### 7.1 문의하기

웹 `/contact`의 본문을 그대로 쓴다. 마스코트 이미지, 안내 문구, 메일 주소,
「메일 보내기」 버튼, 「다른 메일 앱으로 보내기」 링크까지 동일하다. 헤더와 푸터만
없다.

### 7.2 개인정보 처리방침 · 이용약관

웹 버전을 출발점으로 삼되 앱에만 있는 것을 반영해 새로 쓴다. 웹 버전은 "로그인 없는
익명 식별자 + 음성 녹음 + 만족도 조사" 기준으로 쓰여 있다. 앱에 추가되는 것은
다음 세 가지다.

**푸시 알림** — 학습 알림 수신을 위한 푸시 토큰 발급·저장, 알림 수신 동의와 철회
방법(설정 화면의 토글, OS 알림 설정).

**기기 내 학습 기록 저장** — 앱이 기기에 학습 기록을 저장한다는 사실과, 「모든 학습
기록 삭제」로 파기할 수 있다는 절차.

**액세스/리프레시 토큰** — 로그인 기능은 없지만 이용자 구별을 위해 토큰을 발급받아
기기에 저장한다. 이름이나 이메일이 없어도 그 토큰으로 특정 이용자의 학습 기록과
응시 이력이 계속 연결되므로, 개인정보 처리방침에 명시한다. 리프레시 토큰이 앱 재설치
전까지 지속된다면 사실상 지속적 식별자다. 조문에서의 위치는:

- **자동 수집 항목** — 이용자가 입력하는 것이 아니라 앱이 발급받아 저장하므로.
- **처리 목적** — 로그인 없이 이용자를 구별하여 학습 기록·응시 이력을 연결.
- **저장 위치** — 기기 내 보안 저장소(iOS Keychain / Android Keystore).
- **파기** — 토큰 만료 시, 그리고 「모든 학습 기록 삭제」 실행 또는 앱 삭제 시.

웹 방침(`src/app/privacy/page.tsx`)이 이미 "로그인 없이 브라우저에 저장되는 익명
식별자"를 다루고 있으므로, 앱에서는 그 식별자의 형태가 토큰으로, 저장 위치가 기기
보안 저장소로 바뀐 것을 반영하는 형태가 된다.

6절에서 웹 분석 도구를 걷어냈으므로, 앱용 방침의 위탁·국외 이전·자동 수집 장치
조문에서 Microsoft Clarity와 Google Analytics를 뺀다. 대신 푸시 알림 발송을 위한
FCM·APNs를 위탁·국외 이전 항목에 넣는다. 자동 수집 장치 조문은 조문 번호를
유지하되 "행태정보를 수집하지 않으며, 도입 시 사전 고지한다"는 취지로 바꾼다.

**범위 밖으로 확인된 것** — 회원가입·로그인, 인앱결제·구독. 해당 조문은 넣지 않는다.

> **법률 검토 필요.** 이 문서와 그에 따라 작성될 조문은 법률 자문이 아니다. 웹
> 버전을 기준으로 앱 상황에 맞춘 초안이며, 공개 전에 직접 검토해야 한다.

## 8. 시행일과 버전

앱용 방침·약관은 웹과 본문이 다르므로 시행일도 따로 관리한다. 웹의 `EFFECTIVE_DATE`
상수 방식을 그대로 따라 각 페이지에 상수로 둔다.

음성 동의(`VOICE_CONSENT_VERSION`)와는 별개다. 그쪽은 동의 이력을 남기기 위한
버전이고, 여기는 게시용 시행일 표기다. 섞지 않는다.

## 9. 검증

이 레포에 테스트 프레임워크가 없으므로 다음으로 확인한다.

- `npx tsc --noEmit`, `pnpm lint`, `pnpm format:check`
- 세 경로를 모바일 폭(375px)과 데스크톱 폭에서 육안 확인
- 페이지 안에 앱 밖으로 나가는 내부 링크(`/`, 로고, "홈으로")가 없는지 확인
- `app-*` 경로의 HTML에 Clarity·GA 스크립트가 없고, 웹 경로에는 그대로 있는지 확인
- 문의하기의 외부 링크가 `mailto:` 및 `https://mail.google.com`만인지 확인 —
  RN의 링크 가로채기 대상과 일치해야 한다
