# 블로그 검색을 별도 라우트로 분리한 이유

블로그 검색을 `/blog?q=`가 아니라 `/blog/search?q=`로, 목록 페이지네이션을 `/blog?page=2`가 아니라 `/blog/page/2`로 분리한 이유를 정리한다. 둘 다 원인이 같아서 한 문서에 묶는다.

## 1. 배경

초기 설계(`docs/superpowers/specs/2026-07-29-blog-design.md`)는 검색을 목록 페이지 안에서 처리하려 했다. 검색창에 타이핑하면 화면 전환 없이 카드 그리드만 갱신되고, 상태는 `?q=`로 URL에 반영되는 방식이다. 무한 스크롤의 크롤러용 앵커도 같은 맥락에서 `/blog?page=2`로 잡았다.

이후 `docs/blog.md`(4.3, 21장)가 검색을 `/blog/search?q={검색어}`라는 별도 페이지로 규정하고 있는 것을 확인했고, 그 판단이 옳은지 검토한 결과 분리하기로 했다.

## 2. 결정적인 이유 — `/blog`를 정적으로 유지하기 위해

App Router에서 페이지가 `searchParams`를 읽는 순간 해당 라우트는 **정적 생성 대상에서 빠지고 매 요청 동적 렌더링**으로 전환된다. Next 15부터 `searchParams`는 Promise이고, 이를 `await`하는 것이 곧 동적 렌더링 opt-in이다.

즉 `/blog?q=` 방식을 택하면:

- 사용자가 검색을 쓰든 안 쓰든 목록 페이지 전체가 매 요청 서버 렌더링된다.
- 프리렌더된 HTML이 없으므로 TTFB가 백엔드 응답 시간에 그대로 묶인다.
- LCP는 구글 랭킹 시그널이다. 블로그를 만드는 목적 자체가 검색 유입인데, 가장 많이 색인될 목록 페이지의 속도를 검색 기능 때문에 희생하는 셈이 된다.

경로를 분리하면 `/blog`는 `searchParams`를 전혀 읽지 않으므로 정적으로 굳고, 동적 렌더링은 실제로 그것이 필요한 `/blog/search`에만 남는다.

### 2.1 페이지네이션 경로에도 같은 논리가 적용된다

먼저 오해를 피하기 위해 명확히 해둔다. **무한 스크롤과 `/blog/page/[page]`는 서로 무관하다.** 두 경로는 대상이 다르다.

- **사용자** — `/blog`에 1페이지가 프리렌더돼 있고, 스크롤하면 클라이언트가 백엔드 `/api/posts?page=2`를 직접 호출해 카드를 이어 붙인다. 이 과정에 Next.js 페이지 라우트는 등장하지 않는다.
- **크롤러** — 스크롤하지 않으므로 위 경로가 존재하지 않는 것과 같다. 그래서 `/blog` HTML에 다음 페이지로 가는 실제 `<a>`를 남겨두고, 그 페이지가 또 다음 페이지로 링크를 잇는다. `/blog/page/[page]`는 오로지 이 용도의 표면이다.

이 앵커는 **숨기지 않고 실제로 보이게 둔다.** 목록 하단 안내 문구 아래에 작은 회색 "다음 페이지" 링크로 그려진다. `display: none`이나 `visibility: hidden`으로 크롤러에게만 보여주는 방식은 클로킹으로 취급될 수 있고, 그렇게까지 보지 않더라도 구글은 숨겨진 링크의 가치를 낮게 평가한다. 눈에 띄지 않게 만드는 것과 감추는 것은 다르다. 덤으로 JS가 동작하지 않는 환경과 키보드 사용자에게는 이 링크가 다음 페이지로 가는 유일한 수단이 된다.

문제는 이 크롤러용 앵커를 어디에 매다느냐가 `/blog`의 렌더링 방식을 바꾼다는 점이다. `/blog?page=2`는 `/blog`와 **같은 라우트**이므로, 한 파일이 `searchParams.page`를 읽어 몇 페이지인지 판단해야 하고 그 순간 `/blog`가 동적으로 전환된다. 크롤러용 링크 하나 때문에 가장 많이 색인될 목록 페이지가 정적 렌더링을 잃는 셈이다.

`/blog/page/[page]`는 별개의 라우트 파일이라 `/blog`가 `searchParams`를 건드릴 일이 없다. 덤으로 이 경로들도 `generateStaticParams`로 미리 생성할 수 있다.

### 2.2 새 글이 크롤 경로에 반영되지 않을 위험

"페이지네이션이 빌드 시점에 확정되면, 이후 등록된 글은 크롤러가 따라갈 링크가 없는 것 아닌가"라는 우려가 있을 수 있다. **순수 SSG였다면 실제로 그렇게 된다.** 5절에서 ISR을 택한 이유 중 하나가 이것이고, 다음 세 가지가 각각 이 위험을 막는다.

1. **ISR로 목록 자체가 다시 만들어진다.** `/blog`는 재검증 주기마다 서버에서 재생성되므로 새 글 카드와 하단 다음 페이지 링크가 함께 갱신된다. 재배포가 필요 없다.
2. **`dynamicParams`가 빌드 때 없던 페이지 번호를 받아준다.** 글이 늘어 페이지 수가 3에서 4로 늘면 `/blog/page/4`는 프리렌더돼 있지 않지만, 첫 요청에서 렌더링된 뒤 캐시된다. 이 값을 `false`로 두면 그때부터 404가 나므로 켜둔 상태를 유지해야 한다.
3. **새 글은 애초에 1페이지에 꽂힌다.** 목록이 최신순이므로 새 글은 `/blog` 첫 화면으로 들어오고, 뒤 페이지로 밀리는 것은 오래된 글이다. 페이지네이션은 새 글을 노출하는 장치가 아니라 과거 글이 고아 페이지가 되지 않게 붙잡아두는 장치다.

여기에 `sitemap.xml`이 공개 글 전체를 나열하므로 크롤 경로는 이중으로 확보된다.

## 3. 두 번째 이유 — 색인 정책의 경계가 명확해진다

`docs/blog.md` 13.7의 색인 정책은 다음과 같다.

| 페이지         | 처리              |
| -------------- | ----------------- |
| `/blog`        | `index, follow`   |
| `/blog/{slug}` | `index, follow`   |
| `/blog/search` | `noindex, follow` |

두 지시어는 통제 대상이 다르다. `index`는 **그 페이지 자체를** 검색 결과에 넣을지, `follow`는 **그 페이지 안의 링크를** 따라가고 링크 가치를 전달할지를 정한다.

검색 결과에 `noindex, follow`를 준 이유가 여기서 갈린다. 검색어 조합마다 URL이 무한히 생기는데 그것이 전부 색인되면 내용이 얇고 서로 비슷한 페이지가 대량으로 쌓여(thin·duplicate content) 사이트 전체 평가가 깎인다. 그래서 `noindex`다. 반면 그 페이지에 걸린 것은 실제 글 링크이므로 크롤러가 타고 들어가 글을 발견하는 것은 이득이다. 그래서 `follow`는 유지한다. "이 페이지는 목적지가 아니라 통로"라고 알려주는 셈이다.

비교하자면 `/exam/*`은 `X-Robots-Tag: noindex, nofollow`다. 시험 화면은 통로 역할조차 필요 없어 둘 다 껐다.

`/blog?q=` 방식이면 한 라우트가 `q`의 유무에 따라 index와 noindex를 오간다. 동작은 하지만 조건부 분기라서, 나중에 이 파일을 고치다 분기를 깨뜨리면 검색 결과 페이지가 색인된다. 검색어 조합마다 URL이 무한히 생성되는 페이지가 색인되면 얇은 중복 콘텐츠가 대량으로 쌓이는 전형적인 사고로 이어진다.

경로가 갈리면 `/blog/search/page.tsx`의 metadata에 `robots: { index: false, follow: true }`를 한 번 박아두는 것으로 끝나고, 목록 페이지 쪽은 이 정책을 신경 쓸 일이 없다.

## 4. 검토한 대안

- **같은 라우트에서 `q` 유무로 분기 (기각)**
  위 2·3절의 두 문제를 모두 안는다. 특히 정적 렌더링 상실은 조건부 분기로 우회할 수 없다. `searchParams`를 읽는 것 자체가 트리거이기 때문에, "검색어가 없을 때만 정적"이라는 선택지는 존재하지 않는다.

- **검색을 클라이언트 전용으로 처리 (기각)**
  목록을 정적으로 두고 검색은 클라이언트에서만 API를 호출해 결과를 그리는 방식이다. `/blog`는 정적으로 남지만, 검색 결과에 공유 가능한 URL이 없어지고 페이지네이션·뒤로가기가 어색해진다. `docs/blog.md` 21장의 "검색 결과에 페이지네이션이 적용된다"도 만족하기 어렵다.

- **`/blog/search`로 분리 (채택)**
  목록은 정적, 검색은 동적으로 각자 맞는 렌더링 전략을 갖는다. 색인 정책도 파일 단위로 1:1 대응된다.

## 5. 정적으로 굳히는 범위 — 순수 SSG가 아니라 ISR

> SSR·CSR을 포함한 렌더링 방식 전체의 비교와, 재검증이 런타임에 실제로 하는 일은
> `docs/blog-isr-rendering-strategy.md`에 따로 정리했다. 이 절은 경로 분리 판단에
> 필요한 만큼만 다룬다.

"목록을 정적으로 유지한다"는 말은 빌드 타임에 완전히 못 박는다는 뜻이 아니다. 순수 SSG는 이 프로젝트에서 다음 문제를 일으킨다.

- **예약 발행이 동작하지 않는다.** `docs/blog.md` 5.4는 `published_at`이 미래인 글을 시간이 되면 공개하는 예약 발행을 쓴다. 빌드 시점에 확정된 HTML은 시간이 지나도 스스로 바뀌지 않는다.
- **뉴스레터 링크가 깨진다.** 11.2는 발행 15분 뒤 자동 발송이다. 그 시점에 페이지가 존재하지 않으면 구독자가 받은 링크가 404가 된다.
- **빌드가 백엔드 가용성에 묶인다.** `generateStaticParams`가 빌드 타임에 API를 호출하므로, `output: "standalone"` 도커 빌드 중 백엔드에 접근할 수 없으면 빌드가 실패한다.

그래서 ISR을 쓴다. 사용자가 받는 것은 프리렌더된 HTML 그대로이므로 속도와 LCP 이점은 그대로 가져가면서, 재검증 주기 안에서 콘텐츠가 따라온다.

```ts
export const revalidate = 300; // 5분
export const dynamicParams = true;
```

`generateStaticParams`는 빌드 타임에 API 호출이 실패하면 빈 배열을 반환한다. `dynamicParams`가 켜져 있으므로 미생성 경로는 첫 요청에서 렌더링된 뒤 캐시된다. 빌드가 백엔드 상태에 의존하지 않게 하기 위한 것이다.

재검증 지연(최대 5분)까지 없애려면 on-demand 재검증을 얹으면 된다. 발행 스크립트가 글을 `PUBLISHED`로 전환한 뒤 프론트의 재검증 엔드포인트를 호출해 `revalidatePath("/blog/{slug}")`를 실행시키는 방식이다. 백엔드 발행 흐름이 확정된 뒤 추가한다.

## 6. 트레이드오프

분리하면 시안에서 보여줬던 "타이핑하는 대로 즉시 걸러지는" 체감은 사라진다. 검색어를 넣고 제출하면 `/blog/search`로 이동하는, 한 박자 느린 검색이 된다.

이 손실은 감수하기로 했다. `docs/blog.md` 7.1 기준 MVP 검색은 제목에 대한 단순 부분 문자열 검색이고 서버 왕복이 필요하므로, 애초에 완전한 즉시 필터링이 아니다. 그리고 블로그의 주 진입 경로는 사이트 내 검색이 아니라 구글 검색 결과에서 개별 글로 직접 들어오는 것이라, 사이트 내 검색의 체감을 위해 목록 페이지의 렌더링 전략을 바꿀 만한 가치가 없다고 판단했다.

원한다면 나중에 검색창 아래 제목 몇 개를 미리 보여주는 드롭다운을 얹어 즉시성을 일부 회복할 수 있다. 이 경우에도 제출은 `/blog/search`로 가므로 위 구조는 그대로 유지된다.

## 7. 남은 과제

- 재검증 주기 300초는 임의로 잡은 값이다. 발행 빈도가 낮으므로 더 늘려도 되지만, 예약 발행과 뉴스레터 15분 유예를 고려하면 5분보다 크게 늘리지 않는 편이 안전하다. on-demand 재검증을 붙이면 이 값은 안전망 역할만 하게 되므로 그때 늘린다.
- 검색 결과가 `noindex, follow`이므로 크롤러가 결과 페이지의 링크는 따라간다. 검색 결과에만 존재하고 목록·사이트맵에는 없는 글이 생기지 않도록, 사이트맵이 항상 공개 글 전체를 포함하는지 확인이 필요하다.
